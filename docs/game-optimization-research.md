## Выводы для реализации

| Механизм | Когда возможна польза | Что проверяет GTM PC |
| --- | --- | --- |
| Высокий CPU-приоритет | При конкуренции игры с фоновыми процессами за CPU; не гарантирует рост FPS на свободном CPU | Точный путь, PID и время создания текущего процесса; фактический High; правило CpuPriorityClass=3 для имени EXE следующих запусков |
| Производительная GPU для EXE | Если Windows выбирала интегрированную GPU вместо дискретной | Значение GpuPreference=2 для выбранного пути; фактический выбор драйвера зависит от оборудования |
| SCSKiller shader prewarm | Фризы, вызванные именно компиляцией шейдеров; средний FPS и фризы подгрузки мира могут не измениться | CLI должен распознать игру и вернуть Ready/Stale; после compile требуется Done и повторный статус Warmed |
| MMCSS GPU Priority=8 из ряда твикеров | Оснований обещать эффект нет: Microsoft пишет, что этот параметр пока не используется | В игровой профиль не включён |
| SystemResponsiveness=1 | Microsoft указывает, что значения ниже 10 заменяются на 20, то есть это не обещаемый «резерв 1%» | В независимый игровой профиль не включён |

## Подготовка шейдеров

SCSKiller — отдельный открытый движок, а не источник «волшебных» DWORD. Он читает файлы игры, строит графические конвейеры и компилирует их через графический драйвер до запуска игры. Реализация зависит от GPU, DirectX, движка игры и формата файлов.

Для Source 2 (CS2, Dota 2, Deadlock) исследованный Source2Reader читает shaders_pc_dir.vpk, версии VCS 70–72, и указывает DirectX 11. README SCSKiller ограничивает DX11-прогрев NVIDIA. Эти факты не означают, что любая текущая версия каждой игры будет поддержана: окончательный ответ даёт сам установленный движок.

GTM PC подключает пользовательскую официальную установку SCSKiller, не копирует его исходники или бинарные файлы и не выдаёт его результаты за собственные замеры. Разрешённая последовательность CLI: `--version`, `--help`, `add <selected-exe>`, `status <exact-id>`, `compile <exact-id> --threads 2 --idle`, повторный `status`. Команды recorder, before-after, cache clear и запуск игры не вызываются. У обычного CLI в исследованном исходнике ManageRecorders по умолчанию false.

Неподдерживаемые игры, NeedsRecording и отсутствие подтверждения Warmed не считаются успехом. Игра перед прогревом должна быть закрыта. Логи стадий отображаются как стадии, а не как выдуманный процент выполнения. Для сравнения FPS/фризов на своём ПК нужны одинаковый сценарий, одинаковые графические настройки, драйвер, лимит FPS и замеры времени кадра до/после. Результаты из README SCSKiller принадлежат его автору; GTM PC их не воспроизводил.

## Независимость и проверка

Игровая кнопка принимает только game-gpu/game-priority и не меняет системные твики или питание. Журнал игровых операций хранится отдельно; обычной кнопки отката в игровом интерфейсе нет. Внутренняя транзакционная копия нужна для восстановления при ошибке и проверяется тестами. Никакого Realtime-приоритета, закрытия посторонних программ или внедрения в игру GTM PC не делает.

В Windows CI тестируется не только запись реестра: отдельная копия cmd.exe под именем cs2.exe получает реальный High, второй запуск проверяет сохранённое правило, контрольная сумма системного журнала остаётся прежней. Это проверка механизма на одноразовом runner, не доказательство прироста FPS в настоящей игре или совместимости с каждым античитом. Прогрев настоящих шейдеров требует подходящей GPU и установленной игры; локальные тесты адаптера SCSKiller проверяют протокол и отказ от ложного успеха.

## Исправления интеграции 0.7.4

Команда SCSKiller `status <id>` выдаёт подробный блок: первая строка содержит название и ID, а состояние — отдельная строка `status Ready: ...` или `status Warmed: ...`. Адаптер поддерживает этот формат и табличный вывод, сопоставляет точный ID и не считает имя игры состоянием. Отдельно обрабатывается отказ на stderr при нулевом коде возврата во время обновления SCSKiller. Тесты моделируют фактический формат CLI из указанного выше снимка исходников; они не заменяют проверку GPU и реальной игры.

Файл, явно выбранный пользователем, может иметь любое допустимое имя EXE: имена пресетов больше не служат ограничением. Сохраняются проверка абсолютного пути/расширения, фактического файла при выборе, точного процесса и времени его запуска, а также допустимого целевого ключа CpuPriorityClass при проверке резервной копии.
